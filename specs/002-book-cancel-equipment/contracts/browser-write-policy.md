# Browser Write Policy — SEC-001 Design Amendment

**Date**: 2026-10-14. Targeted amendment to approved D1 for FR-019 / SC-016. Review status: approved by independent [quality review](../team/quality-sec-001-design.md) and [security review](../team/security-sec-001-design.md). Implementation evidence and original reviewer finding closure remain separate gates. Other D1 business, persistence, messaging, retry and identity decisions remain unchanged.

## Threat and boundary

A remote web page, sandboxed frame or opaque origin can send a simple/no-cors POST to a loopback listener even when CORS prevents it reading the response. Manual JSON parsing must not turn text/plain into a booking; bodyless cancellation needs an independent guard. CORS is not the write boundary. Protect every Reservations API POST, including compatibility `/api/hellos`, before its handler performs body parsing, Inventory calls, database reads/writes or publication. Apply the same rule to any future unsafe HTTP method if added; this amendment adds no new endpoint.

The existing application remains unauthenticated on a trusted workstation. Local CLI callers and pages from explicitly listed loopback hosts remain trusted. Origin/Fetch Metadata distinguish browser contexts; they authenticate neither people nor local software, which can forge headers. This is protection from browser content with a foreign/opaque origin, not user isolation. No DNS lookup, remote-host allowlist, permissive CORS or server-only custom proxy-header exception is introduced.

## Ordered server admission algorithm

1. Require a loopback request authority: HTTP or HTTPS request scheme and Host exactly `localhost`, `127.0.0.1` or `[::1]`, with omitted default port or numeric port 1..65535. Match host case-insensitively; reject trailing dot, subdomains, arbitrary DNS aliases, noncanonical IP spellings, IPv4-mapped IPv6, credentials, malformed/multiple authorities and port0. Validate parsed authority without resolving DNS. Do not replace Host/scheme with untrusted Forwarded/X-Forwarded headers. All actual transport listeners and proxies must remain loopback as already required.
2. If any Origin header is present, require exactly one nonempty serialized origin. Accept only `http://localhost[:port]`, `http://127.0.0.1[:port]`, `http://[::1][:port]`, or their `https://` equivalents, with valid omitted default/numeric port 1..65535. Match scheme/host case-insensitively, require canonical authority spellings above; value has no path/trailing slash, query, fragment, userinfo, comma/space-separated list or embedded whitespace. Reject literal `null`, empty/malformed/duplicate Origin and every other host/scheme. Bound origin parsing to 128 characters. Rejection is403 even if Fetch Metadata says same-origin or the submitted Host is loopback.
3. If Origin is absent, reject403 when **any** request header name starts `Sec-Fetch-` (case-insensitive), irrespective of value (including empty/none/same-origin), or when Referer is present. These are browser-like requests lacking trustworthy origin evidence; do not grant a fallback based on Fetch Metadata, Referer, user-agent or spoofable proxy headers. Origin absence with no such browser metadata is accepted only under step1, for direct local CLI/test clients. A User-Agent alone is neither an authorization signal nor a browser classifier.
4. For an accepted Origin, Fetch Metadata does not broaden or replace its host allowlist. A trusted loopback origin may carry same-origin, same-site or cross-site metadata because ports and localhost/127.0.0.1/::1 aliases can differ. Foreign/opaque Origin always rejects. Older clients with a valid loopback Origin remain accepted if Fetch Metadata is absent. Originless browser-like requests remain rejected.
5. After admission, POST `/api/reservations` requires one parsed Content-Type `application/json` (case-insensitive), optionally `charset=utf-8` (quoted/case-insensitive allowed); no other parameters/charset, malformed/multiple media types, absent type or other subtype is accepted. Reject415 before reading JSON, contacting Inventory or the database. This feature does not accept vendor +json types. Existing 4 KiB size bound and strict generated JSON/date validation follow. POST cancellation is bodyless and requires no JSON media type: admission alone must protect it independently. Preserve the legacy hello payload/media contract after the shared admission guard.

Every admission/media rejection leaves reservation rows, status, outbox rows and broker publication unchanged. Safe error telemetry may record bounded reason/outcome only; never record raw Origin/Referer/headers/body or turn origin strings into metric dimensions.

## Proxy compatibility and accepted contexts

The actual `src/Web/proxy.conf.cjs` uses `changeOrigin:false` and a fixed loopback Reservations target. The browser POST to the printed Web URL supplies Origin for Web, and the proxy forwards it/Fetch Metadata; Host normally remains the Web authority although the backend listens on a different port. The policy independently checks both authorities against the canonical loopback allowlist; it does **not** compare Origin port to backend listener port, and remains compatible if a loopback proxy changes Host to the backend authority. Preserve Origin/Fetch Metadata end-to-end; dropping them is not an implementation fix.

All ports 1..65535 on the listed hosts are trusted under the explicit trusted-workstation scope. Thus a page served by trusted local software at another loopback port may issue a write; this is an intentional local trust rule, not a claim to isolate other local applications. Remote DNS names remain rejected even if they resolve to127.0.0.1, equal a forged Host, or have localhost as a suffix. Normal supported browser journey uses the printed HTTP Web URL. HTTPS localhost origins are valid policy inputs if trusted local HTTPS tooling is used; this does not add HTTPS hosting or change current startup.

Direct curl/.NET test clients use loopback request Host, omit Origin and all Sec-Fetch-* / Referer, and supply application/json for reservation creation. These remain compatible with existing API tests and documented local calls. Tests must set loopback Host explicitly where WebApplicationFactory defaults differ. A direct client adding a foreign Origin is rejected regardless of being a CLI; clients must not delete browser metadata in a proxy to gain admission.

## Safe errors and precedence

Admission403: Problem Details title `Browser write not allowed`, code `browser_write_forbidden`, detail `Use the local application or a direct local API client.` Media415: title `JSON content type required`, code `unsupported_media_type`, detail `Send application/json encoded as UTF-8.` Do not reflect origin, request authority, upstream diagnostics or input. Admission precedes media/identifier/date validation so rejected cancellation cannot reveal whether a reservation exists and hostile text/plain creation returns403 rather than a misleading business result. An admitted local text/plain creation returns415. Existing business statuses/codes follow for admitted JSON/no-body requests.

## Primary references

[WHATWG Fetch Origin/CORS rules](https://fetch.spec.whatwg.org/#origin-header) distinguish request origin and response sharing. [W3C Fetch Metadata](https://www.w3.org/TR/fetch-metadata/) provides browser request-context headers. [RFC6454 serialized origin](https://www.rfc-editor.org/rfc/rfc6454#section-7) defines the scheme/host/port representation. The allowlist/fallback and media policy above are deliberate local application choices derived from these mechanisms, not an authentication claim.
